# apps/tv instructions

The Samsung Tizen TV app: pure DOM, no framework. It pairs by QR code, then plays the slides from the Convex HTTP API using `@j-os/tv-player`.

- **No secrets.** The device token is stored in `localStorage` through `src/storage.ts` and sent only as a `Bearer` header. Never render, log or put it in a URL. The QR carries only the one-time code.
- **The API allows 600 requests an hour per device.** `src/sync.ts` polls the manifest once a minute and downloads the pack (`/tv/pack`) only when `packVersion` changes (or, before a pack exists, refetches only slides whose `rev` changed). Keep it that way; tests guard it. The pack version stored is the one in the download's `X-Tv-Pack-Version` header, not the manifest's.
- **A broken pack is not re-downloaded every minute.** `src/sync.ts` remembers the pack version that failed to load and waits 5 minutes, doubling up to an hour, unless the version changes; a success resets it. Keep the last good pack playing.
- **The power schedule rides the manifest tick: no second poll.** `src/scheduleSync.ts` fetches `/tv/schedule` only when the manifest's `scheduleVersion` changes; the XML is capped at 16 KiB (`src/schedule.ts`). A failed fetch or parse backs off 5 minutes, doubling to 60, per version. The last good schedule persists in localStorage (`jfloor-tv-schedule`, via `src/storage.ts`) so an offline reboot still follows it; a null `scheduleVersion` clears it. A schedule problem never blocks the slides.
- **"Off" is a black cover, not a panel power-off.** `src/power.ts` adds a CSS class that hides the app; the TV stays powered and the manifest poll keeps running. A real power-off needs a spike on the real TV (Tizen power or B2B APIs, backlight, HDMI-CEC): none is verified. Do not claim more.
- **Pack memory is unmeasured.** A swap keeps the old and new pack resident (HTML slides with data: URIs, blobs) plus a build transient with the zip (up to 40 MiB); see "Memory on the TV" in `README.md` and its manual worst-case step. Do not claim it was measured. No unbounded caches: the data: URI cache lives for one load.
- **Chrome 76 is the runtime; the build lowers syntax, not APIs.** `Element.replaceChildren`, `replaceAll`, `.at()`, `Object.hasOwn`, `structuredClone`, `AbortSignal.timeout`, CSS `inset` and flex `gap` all fail on the TV and pass in CI. ESLint bans the known names (`eslint.config.js`) and `src/chrome76.setup.ts` removes the DOM ones in tests; add to both when you find another. Do not rely on them being caught: check a new API's Chrome version.
- **Every request has a timeout** (`src/api.ts`: 30 s, 5 min for the pack) linked to the sync's stop signal. A failed pack download, build or player call revokes what it built and backs off.
- **HTML slide assets are inlined as data: URIs** (`src/pack.ts`); blob: URLs are only for image slides, which the player draws outside the sandboxed frame. That data: loads and blob: does not in the sandboxed srcdoc frame was observed only in headless Chromium 152: unverified on Chrome 76 / a real TV. The HTML strings of one pack are capped in total (`HTML_TOTAL_MAX_CHARS`, 96 MiB, unmeasured).
- **Failures keep the last slides playing.** 429 and network errors are retried on the next tick; 401 drops the token and re-enters pairing.
- **Slides are untrusted.** HTML goes to the player as a string; the player owns the sandboxed iframe. Never use `innerHTML` for slide content.
- **No inline styles from JS.** Styling lives in `src/app.css` (and the player's own CSS).
- **Build-time env:** `VITE_TV_API_URL` and `VITE_TV_APP_URL` are required; the build fails without them. Use placeholders (`example.com`) in tests and docs: this repo is mirrored publicly.
- The build emits a classic `<script>` (not a module) because the TV loads `index.html` from a file origin.
- It cannot be tested in CI on a real TV: see `README.md` for the manual steps.
